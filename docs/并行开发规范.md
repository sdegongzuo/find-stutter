# 多任务并行开发规范（find-stutter）

> 目标：多个 AI 会话 / 多个任务同时开发时，杜绝**代码冲突、编译冲突、运行冲突、测试冲突**。
> 本文中的「运行测试冲突」按两层理解：§4 是跑 GUI/服务/CLI 时的运行时资源争抢，§6 是 `cargo test` 进程之间的争抢。

## 0. 结论先行

代码、运行、测试三类冲突靠隔离消除；**编译与编译后验证靠「唯一 target + 单一队列」串行**；系统级独占资源隔离不了，只能登记后串行。

采用**轻量默认**：不为每个 worktree 建 target（现有 `target/` 19G，×N 太重），全机只有一个 target、一条构建队列。编译与测试是同一条流水线的两个阶段，角色可以分开，执行必须排队。

| 冲突类型 | 隔离手段 | 能否彻底隔离 |
| --- | --- | --- |
| 代码冲突 | 一任务一 worktree 一分支 + 文件所有权矩阵 + 共享文件主线独占 | 能 |
| 编译冲突 | **唯一 `CARGO_TARGET_DIR` + 单一构建队列**（§3） + RTK 统一 | 能（靠串行） |
| 运行冲突 | 私有 config → 私有 DB / 私有日志 + 禁自动拉服务 | 能 |
| 测试冲突 | 与编译同一队列、不并发 + 修掉 6 个固定临时文件名 + 基线对照 | 能（靠串行） |
| 系统级独占（服务 / ETW / 桌面 CSV） | 独占窗口登记，一次一个任务 | **不能，只能串行** |

现状盘点（2026-11-04 实测）：

- 仓库只有 1 个 worktree、1 条 `main` 分支，本地领先 `origin/main` 6 个提交；调研期间从 ahead 5 变成 ahead 6，说明并行提交已在发生。
- `target/` **19G**，D 盘可用 306G；根目录 `stutter.db` 110M + `stutter.db-wal` 5.1M，是被服务持续写入的真实库。
- 共 566 个 `#[test]`，其中 6 处使用**固定系统临时文件名**，跨进程会互删。
- 全系统唯一资源：`FindStutter` SCM 服务、`NT Kernel Logger`、`find-stutter-net` 两个 ETW 会话。
- 零环境变量可覆盖 config / DB / 日志路径；`Config::load("config.toml")` 在 13 处调用点写死。

## 2. 代码冲突：worktree + 所有权矩阵

### 2.1 目录与分支（位置固定，不临时另建目录）

```
主线      D:\dev\cli\find-stutter                    (main，只做集成/发布/共享文件)
任务 N    D:\dev\cli\find-stutter-wt\<task-id>       (task/<task-id>)
```

```bash
TASK=rc2-fields
GIT="D:/app/Git/cmd/git.exe"
"$GIT" worktree add -b "task/$TASK" "D:/dev/cli/find-stutter-wt/$TASK" main
```

规则：

- 一个 worktree 只对应一个分支、一个任务；**禁止两个 worktree 挂同一分支**（git 本身会拒绝）。
- 新分支一律从 `main` 拉，禁止基于别人的任务分支再拉分支，除非在登记表里写明依赖。
- 任务做完立刻 `git worktree remove "D:/dev/cli/find-stutter-wt/<task-id>"`；coding worktree 不产生 `target/`，无需额外清理。
- 建议同时进行中的 worktree **3–5 个**：轻量模式下磁盘不再随 worktree 数增长（只有 §3 的一个 target），瓶颈变成构建队列的排队长度与文件所有权冲突。

### 2.2 文件所有权矩阵

| 范围 | 谁能改 |
| --- | --- |
| `crates/core/src/*` | 声明了 core 的任务独占 |
| `crates/ui/src/*`、`crates/ui/ui/overlay.slint` | 声明了 ui 的任务独占 |
| `crates/cli/src/*`、`crates/service/src/*`、`crates/bin/src/*` | 各自任务独占 |
| `Cargo.toml`（根 + 各 crate）、`Cargo.lock`、`config.toml`、`AGENTS.md`、`BUILD.md`、`README.md`、`UPGRADE.md`、PRD / `docs/adr/*` | **只有主线能改** |

- 任务分支需要加依赖 / 改配置 → 在登记表里写「申请」，由主线统一改并合回，任务分支 rebase 后继续。
- **`Cargo.lock` 是最高频冲突源**：任务分支禁止执行 `cargo add` / `cargo update` / 升级依赖；不允许提交 `Cargo.lock` 的变更。集成时若发生 lock 冲突，一律以 `main` 为准（`git checkout main -- Cargo.lock`）后重跑 `rtk cargo check` 生成差异，且只在主线提交。
- 提交前越界自检，把输出和登记表里声明的所有权逐行对照：

```bash
"$GIT" diff --name-only main...HEAD
"$GIT" status --short        # 顺带确认没有误碰 config.toml / Cargo.lock
```

- 提交信息一律中文；只提交本任务范围内的文件，不要 `git add -A` 把并行会话的改动一起带走。
- 同步节奏：每次开工 `git fetch`；超过一天的分支 `git rebase main`。合并前先在任务分支跑完 §6 的测试，再回主线 `git merge --ff-only task/<id>`（或走 PR）。
- **永远不要 `git push` 别人的分支，也不要在任务分支上 push `main`**。

## 3. 编译冲突：唯一 target + 单一构建队列（轻量默认）

### 3.1 布局：N 个 coding worktree，1 个 build worktree，1 个 target

```
D:\dev\cli\find-stutter             主线：只做集成与提交，不再编译
D:\dev\cli\find-stutter-wt\<id>     coding worktree：无 target，禁止执行任何 cargo 命令
D:\dev\cli\find-stutter-build       build worktree：唯一能跑 cargo 的目录
D:\dev\cli\find-stutter-build\target   唯一 CARGO_TARGET_DIR
```

- 执行 Agent 只在自己的 coding worktree 写代码，**不编译、不测试**；完成后交出分支名 + commit hash。
- 编译/测试 Agent 在 build worktree 里 checkout 这个 hash，拿到的是**冻结快照**，不会读到改到一半的文件。任务分支的 commit 对象在同一个 `.git` 里，直接 checkout 即可，无需 push。
- 主线现有 `target/` 19G 是现成缓存：停掉占用 exe 的 GUI/服务后，同盘把它移动到 build worktree 位置（rename 瞬时）即可复用；否则让队列冷启动预热一次。
- **禁止把 `CARGO_TARGET_DIR` 指到 C 盘**（用户约定）。

### 3.2 排队必须覆盖「整段流水线」，不能只靠 cargo 自带锁

cargo 的 build directory lock **只在单个 cargo 命令执行期间持有**：`cargo test` 编译完就释放锁，之后才运行测试二进制。这个空窗里另一个 `cargo build` 可以进来重新链接、覆盖 exe —— 测试跑的可能是被换掉的二进制，或直接 `os error 5`。

所以互斥锁由**队列**持有，覆盖整段：

```
checkout 冻结快照 → clean -p → cargo check/build → cargo test → 收集日志 → reset 回 main
```

编译与测试是同一条流水线的两个阶段：角色可以分开（社区实践「构建者不自验」），**执行必须串行**，一次只有一个 job。

### 3.3 队列协议

交互原则是「**不传代码，传 commit hash**」。三类通道分开：

| 通道 | 载体 | 谁写 |
| --- | --- | --- |
| 控制面 | `.workbuddy/parallel/board/<task-id>.md`，一任务一文件 | 总控唯一写者 |
| 数据面 | git（分支 / commit hash = 唯一真相） | 执行 Agent 写自己的分支 |
| 结果面 | `.workbuddy/parallel/queue/<task-id>.json`、`results/<task-id>.log`，只追加不改写 | 队列 worker / 编译 / 测试 Agent |

`queue/<task-id>.json` 字段：`task_id`、`commit`、`base_commit`、`pkg`、`test_target`、`kind`（`try` 只验证不合并 / `merge` 验证通过后提交）、`requested_at`、`state`。
状态机 `pending → queued → building → testing → approved → merged`，失败进 `failed` 并退回执行 Agent。
顺序 FIFO；`try` 可插队但结果不触发合并；小改动可打包成 `rollup` 批次一起测。

消息类型：`TaskAssigned`（总控→执行，带 base commit 与文件租约）、`ChangeReady`（执行→队列，带 commit hash）、`BuildResult` / `TestResult`（带日志路径，不带源码）、`MergeApproved`、`RebaseRequired`。

### 3.4 锁：MCP Agent Mail build slot + 重试队列（已落地）

不再手写 `mkdir` 锁，改用 §9 装的 Rust 版 MCP Agent Mail：它提供 TTL 文件租约、pre-commit guard、Git 审计，`am am-run` 把整段命令包在租约里。

**两个实测坑（2026-11-04）**：

1. `WORKTREES_ENABLED` 默认 `false`。不设成 `true` 时 `am am-run` 打印 `build slots are disabled ... running without a slot lease or conflict check`，命令照跑但**根本没锁**，是假排队。
2. `--block-on-conflicts` 名字有误导：遇到冲突时是**直接 abort**（`build slot conflicts detected and --block-on-conflicts set; aborting.`），并不等待。FIFO 排队必须由外层重试循环提供。

所以队列入口统一为 `/d/tools/parallel/queue-worker.sh`（§9.2）：抢不到槽按 `QUEUE_RETRY_SECS` 重试到 `QUEUE_WAIT_SECS` 超时；只有识别出「槽冲突」才重试，命令本身失败如实上报退出码，绝不吞掉。

```bash
JOB_ID=rc2-fix AGENT_NAME=exec-1 /d/tools/parallel/queue-worker.sh \
  rtk cargo test -p find-stutter-core --lib --test integration_test -- --test-threads=2
```

并发实测：A 持槽 `sleep 3`；B 第 1 次 `conflicts detected`、2 秒后重试、第 2 次拿到槽成功。artifacts 落 `command.json` / `stdout.log` / `stderr.log` / `exit_code.txt` / `result.json`。

- 超时兜底：worker 默认 900s 等待上限，超时退出 75 并保留日志，不自动续跑。
- 拿到锁的是队列 worker；编译 Agent 和测试 Agent 只是 worker 里的两个阶段，**不各自抢锁**。
- 降级备选（无 Agent Mail 时）：`mkdir "$LOCK" 2>/dev/null || exit 75` + `trap 'rmdir "$LOCK"' EXIT`，原子且 Windows 可靠，但没有租约审计；不要用「先检查存在再创建」的 TOCTOU 写法。

### 3.5 单个 job 的标准步骤（worker 独占执行）

```bash
set -o pipefail        # 关键：tee 管道不能吞掉 cargo 的退出码
GIT="D:/app/Git/cmd/git.exe"
export BUILD="/d/dev/cli/find-stutter-build"
export CARGO_TARGET_DIR="$BUILD/target"     # 全机唯一
export CARGO_BUILD_JOBS=2                   # 重链接改 1
export PATH="/d/app/cargo/bin:$PATH"
export FIND_STUTTER_SKIP_SERVICE=1

"$GIT" -C "$BUILD" checkout --detach "$COMMIT"   # 冻结快照
cd "$BUILD"
rtk cargo clean -p find-stutter-core -p find-stutter-ui -p find-stutter-cli \
                -p find-stutter-bin -p find-stutter-service
rtk cargo check -p "$PKG"                    2>&1 | tee "$RESULTS/$TASK-build.log"
rtk cargo test  -p "$PKG" --lib --test "$TEST_TARGET" -- --test-threads=2 \
                                                  2>&1 | tee "$RESULTS/$TASK-test.log"
"$GIT" -C "$BUILD" checkout main
"$GIT" -C "$BUILD" reset --hard origin/main   # 只在 build worktree 用，禁止在主线/coding worktree 执行
```

两个不可省的步骤：

- **`cargo clean -p`（只清 workspace 自己的 5 个 crate，保留第三方依赖缓存）**：共享 target 跨分支时 cargo 用 mtime 判断 fresh，可能直接复用上一个任务的 rlib，**构建通过但链接的是别的任务的代码**（Zcash zebra issue #11589, 2026-10 实测）。这是最危险的静默错误。
- **job 结束必须 reset 回 main**：否则下一个 job 会带着上一个分支的代码起步。

### 3.6 失败、退回与提交闸门

- 单 job 失败**不自动重试**（flaky 会被重试掩盖），标记 `failed` + 附日志路径退回执行 Agent；队列继续处理下一个 job。
- 提交 Agent 只在 `BuildResult` 与 `TestResult` 全绿、且 `base_commit == main HEAD` 时 `git merge --ff-only`；main 已前进就发 `RebaseRequired` 退回重测（对应 bors 的 `ApprovedShaMismatch` 检查）。
- 串行队列的吞吐是硬瓶颈：Rust 官方当年因一轮 CI 3.5 小时，bors 一天最多合 7 个 PR。本项目 566 个测试里有 `sleep(1200ms)` 的慢用例，必须靠 `try` 预检、限定 `-p` / `--test` 范围、`rollup` 批次控制队列长度，不要让两行改动也排全量测试。

### 3.7 通用约束（两种模式都适用）

- `CARGO_BUILD_JOBS=2`（全量重链改 1）。本机 32G 内存 + 16G 页面文件，并发链接会触发 `LNK 0xc000012d` / `os error 1455`；看到 `can't find crate` / `invalid metadata files` / `trait not in scope` 这类假编译错误先怀疑内存不足，别去改代码。
- 任务分支**不跑 `--release`**：根 `Cargo.toml` 开了 `lto="thin"` + `codegen-units=1`，全量 release 慢且吃内存；release / `upgrade` 只在主线做。
- `crates/ui/build.rs` 生成的 Slint 代码落在共享 `OUT_DIR`，由队列串行保证不被并发覆盖。
- PowerShell 里调 RTK 前补齐环境（默认 PATH 里没有 toolchain）：

```powershell
$env:RUSTUP_HOME="D:\app\rustup"; $env:CARGO_HOME="D:\app\cargo"; $env:PATH="D:\app\cargo\bin;$env:PATH"
```

- 文档矛盾待主线统一：`BUILD.md:7-8` 写「裸 cargo 亦可」，`AGENTS.md:14` 与 `UPGRADE.md:124` 要求必须 RTK。以 `AGENTS.md` 为准。

### 3.8 备选：重量模式（不默认）

若某任务必须频繁自测（如大规模重构），可临时给它独立 `CARGO_TARGET_DIR=<wt>/target`，但必须在 board 登记、遵守磁盘预算（19G × N，D 盘可用 306G，≤3 个），且**不得与构建队列同时运行**。默认一律走轻量模式。

## 4. 运行冲突：私有 config 沙箱

### 4.1 路径推导链（现状）

`Config::load("config.toml")`（`crates/core/src/types.rs:1047`）→ `db_path` 相对值按 **config 所在目录**解析成绝对路径（`types.rs:1089-1105`）→ `gui.log` 也锚定 config 目录（`crates/ui/src/logging.rs:21,45`）。

所以：**只要让每个 worktree 加载自己的 config，DB、WAL、SHM、日志就自动各自一份**。但 `config.toml` 是被跟踪文件，直接改它会产生 diff。

### 4.2 推荐做法（需主线做一次小改造）

主线在 `Config::load` 入口加一个环境变量覆盖，约 8 行：

```rust
// FIND_STUTTER_CONFIG 指向的文件优先于默认的 "config.toml"
let path = std::env::var("FIND_STUTTER_CONFIG").unwrap_or_else(|_| path.to_string());
```

各任务把私有配置放到 `<wt>/.workbuddy/sandbox/config.toml`（`.workbuddy/` 已忽略，不进 git），内容：

```toml
[storage]
db_path = "D:/dev/cli/find-stutter-wt/<task-id>/.workbuddy/sandbox/stutter.db"  # 绝对路径
auto_start_service = false
```

启动一律：

```bash
export FIND_STUTTER_CONFIG="$WT/.workbuddy/sandbox/config.toml"
export FIND_STUTTER_SKIP_SERVICE=1     # 双保险，彻底不碰 SCM / 不弹 UAC
rtk cargo run -p find-stutter -- ...
```

### 4.3 不改代码时的过渡做法（不推荐，仅应急）

任务分支本地改 `config.toml` 的 `db_path` + `auto_start_service`，**禁止提交**，收工前 `git checkout -- config.toml` 还原。这是绕过式做法，容易被 `git add -A` 带进提交，主线应尽快做 §4.2。

### 4.4 运行期硬规则

- 主线根目录 `stutter.db`（110M）是真实采集数据，任何任务**只读参考**，禁止写、删、`VACUUM`（`VACUUM` 需独占锁）。
- 任务 worktree **禁止执行** `find-stutter-service install-start` / `restart` / `upgrade`：`crates/cli/src/upgrade.rs:157-231` 会停掉全局服务、在发现的仓库根全量 release 构建、再用 `current_exe()` 重注册服务——谁最后跑谁赢，其他会话的服务立刻失效。
- 桌面固定名 CSV `USERPROFILE\Desktop\卡顿事件_今日.csv`（`crates/ui/src/analysis.rs:1620-1635`）并行期间不要点导出；主线应改成可配置目录。
- 日志 `find-stutter-service.diag.log` 写 exe 同目录；轻量模式下只有 build worktree 产 exe，coding worktree 不运行 GUI/服务，因此不冲突。任务自己起 GUI 时按 §4 走私有 config 沙箱。

## 5. 系统级独占资源：登记后串行（隔离不了）

| 资源 | 证据 | 争抢后果 |
| --- | --- | --- |
| SCM 服务 `FindStutter` | `crates/service/src/install.rs:99`、`service.rs:437` | 谁最后注册谁生效，别的 worktree 二进制被顶掉 |
| ETW `NT Kernel Logger` | `crates/core/src/stack_sampler.rs:48,355` | 全系统唯一，第二个进程采样恒为空 |
| ETW `find-stutter-net` | `crates/core/src/net_tracer.rs:221-222,382` | 同名会话仅一个实例 |
| UAC 提权 / 自动拉服务 | `crates/ui/src/auto_start.rs:109` | 多 GUI 同时弹 UAC、抢同一个服务 |
| 桌面 CSV 固定名 | `crates/ui/src/analysis.rs:1634` | 互相覆盖 |

**独占窗口**规则：

1. 只有主线 / 专门的集成环境允许跑真实采集、装服务、重启、`upgrade`。
2. 需要验证服务或 ETW 的任务，先在 `D:\dev\cli\find-stutter\.workbuddy\parallel\runtime.lock` 写一行
   `<task-id> | <PID> | <开始时间> | <用途>`；文件已存在就等，不要并发跑。用完删掉并注明结束时间。
3. 拿锁期间其他任务只跑纯库逻辑 + 单元测试，不启动任何采集进程。
4. CI / 自动测试统一 `FIND_STUTTER_SKIP_SERVICE=1` 或 `auto_start_service=false`。

## 6. 测试冲突：唯一化临时资源 + 基线对照

### 6.1 必须修的 6 个固定临时文件名（同进程与重量模式下互删）

| 文件 | 位置 |
| --- | --- |
| `find_stutter_test_config.toml` | `crates/core/tests/integration_test.rs:99` |

### 6.2 跑法

```bash
export CARGO_TARGET_DIR="$WT/target"; export CARGO_BUILD_JOBS=2
rtk cargo test -p find-stutter-core --lib --test integration_test -- --test-threads=2
```

- 只跑改动相关的包 / 测试目标，别动不动全 workspace：566 个测试里有 `sleep(1200ms)` 的慢用例（`crates/core/src/detector.rs:1337` 起多处），全量跑既慢又占内存。
- `--test-threads=2` 与全局并发限制配合；出现 `LNK` / `os error 1455` 就降到 1。
- 轻量模式下全机只有一份测试二进制、队列串行执行；但 `%TEMP%` 是系统共享的，同进程并行测试和 §3.8 重量模式仍会撞，所以 §6.1 必须修。
- `crates/ui/src/auto_start.rs:504` 的 `ENV_LOCK: Mutex<()>` 只在本进程内串行，跨进程无效；Windows 环境变量是进程级，本身不构成跨 worktree 冲突，**不要为它加全局锁**。
- 测试库各自独立后，`VACUUM` 独占、`busy_timeout` 竞争都不再是问题。

### 6.3 基线对照（区分目标失败与既有失败）

开工时在主线、收工时在任务分支，跑**完全相同范围**的测试，输出存到任务私有目录（D 盘，不进 git）：

```bash
rtk cargo test -p find-stutter-core --lib --test integration_test -- --test-threads=2 \
  > "$WT/.workbuddy/baseline-before.log" 2>&1
```

对比失败用例名：只有「基线通过、任务分支失败」才算本次改动引入的回归；基线本就失败的、或并行会话导致的环境失败，单独标注，不要混为一谈。

## 8. 每个会话的检查表

**开工**

1. `git status --short --branch`，确认当前分支与基线 commit。
2. 读 `.workbuddy/parallel/board/`，写自己的 `<task-id>.md`，确认文件所有权无交集、独占资源无人占用。

**收工**

1. `git diff --name-only main...HEAD` 对照所有权白名单，确认没碰共享文件。

5. `git worktree remove`；确认队列已把 build worktree `reset` 回 main、build slot 租约已释放。coding worktree 本来就没有 target，无需清理。

## 10. 总控会话运行手册

### 10.1 能力边界（先澄清三个常见误解）

- 总控会话**能派生 teammate**：每个是独立上下文、可并行、有自己的工具权限。但它们是**同一个团队内的代理**，不是 IDE 里新开一个聊天窗口 / session 标签页；用户不会看到每个 teammate 的对话。
- **工具层不会自己起会话**。Agent Mail（租约/邮箱）、Beads（任务图）、`queue-worker.sh`（构建队列）都只是被调用的工具；「拆任务 → 派生 teammate → 分配 worktree」必须由总控会话按规则执行。
- **不会自动建 worktree / 自动汇报**。worktree 路径、分支、环境变量都要在派发消息里写死；teammate 的普通文本输出**用户和总控都看不到**，必须用消息回报。teammate 结束时有自动 idle 通知给总控，但总控只在自己的回合里输出，不会主动弹窗推送进度。

### 10.2 可复制的总控 prompt（粘到总控会话开头）

```text
你是 find-stutter 的总控会话，只做编排，不直接写代码。

每次收到任务：
1. 读 AGENTS.md 与 docs/并行开发规范.md；确认 git status 干净，记录基线 commit。
2. 用 br 建任务与依赖；在 .workbuddy/parallel/board/<task-id>.md 登记文件所有权，
   确认与其它「进行中」条目无交集，有交集就换任务或等待。
3. 按耦合把任务切成互不重叠的子任务，每个子任务派生一个 teammate（唯一名字）。
   派发消息里必须写死：worktree = D:\dev\cli\find-stutter-wt\<task-id>、
   分支 = task/<task-id>、开工先 source /d/tools/parallel/env.sh、
   coding worktree 禁止执行任何 cargo 命令、共享文件只有主线能改、提交信息一律中文。
4. teammate 写完只交出分支名 + commit hash，不自己编译测试。
   由你排队验证：JOB_ID=<task> AGENT_NAME=<会话> /d/tools/parallel/queue-worker.sh <验证命令>。
   每次切分支 clean -p 清 5 个 workspace crate，job 结束 reset 回 main（§3.5）。
5. 队列绿了以后：推 task/<id> 分支 → 开 PR → 等 Actions test 绿 → 打 ready-to-queue label。
   禁止本地 git merge --ff-only 或 push main；main 的唯一写者是合并队列（§9.5）。
6. 汇报节奏：每收到一个 teammate 消息或 idle 通知，就在你的回复里输出一行进度表
   （任务 / 状态 / worktree / 验证结果 / 阻塞）。全部完成或出现失败时输出总结：
   改了哪些文件、测试结果、未解决风险、下一步。不要把 teammate 原始输出贴给用户。
7. 失败不自动重试；退回对应 teammate 并附队列日志路径，明确区分「本次回归」与「既有失败」。
```

### 10.3 进度是怎么传到用户手里的

| 动作 | 用户能否看到 |
| --- | --- |
| teammate 写普通文本输出 | **看不到**（总控也看不到） |
| teammate 发消息给总控 / 更新共享任务列表 | 总控收到，用户仍看不到 |
| teammate 结束的 idle 通知 | 自动送达总控 |
| 总控在自己回合里按第 6 条输出进度表 / 总结 | **这才是用户看到的汇报** |

所以要「一定汇报」，靠的是上面 prompt 的第 6 条约束，不是平台自动推送。若需要**定时**主动汇报（例如每 30 分钟一条进度），那属于另一个需求，要单独配定时自动化，本规范不默认开启。

### 10.4 最短使用方式

把 §10.2 的 prompt 粘到总控会话开头，之后确实只需要下发任务。但首次要先确认 §9.6 的外部动作已就绪（MCP Trust、Mergify App、build worktree 与唯一 target、分支保护），否则 teammate 会在租约或验证队列处卡住。
